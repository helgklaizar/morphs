# 🤖 Инструкции и правила для ИИ-агентов (AGENTS.md)

Добро пожаловать, ИИ-агент! Данный файл содержит обязательные правила, стандарты разработки и соглашения для работы над проектом **BOS Agent (ai-business-os)**. Ознакомьтесь с ними перед внесением любых изменений.

---

## 1. Стек технологий и окружение

Проект представляет собой автономную систему агентов для сборки B2B SaaS.
* **Язык**: Python 3.12+ (совместим с 3.11+)
* **Асинхронность**: Асинхронный Python (`asyncio`)
* **Базы данных и хранилища**:
  * **SQLite** (базовое состояние задач и мутаций)
  * **LanceDB** (векторная память для RAG, размерность 384)
  * **Kùzu** (графовая база данных для AST-анализа кода)
  * **Redis** (шина сообщений EventBus для P2P-координации агентов)
* **ASGI Сервер**: Granian (высокопроизводительный сервер на Rust) / Uvicorn (для разработки)
* **Анализ/Тестирование/Качество**:
  * **Pytest** (тестирование)
  * **Ruff** (быстрый линтер и форматировщик)
* **Безопасность (Red-Team)**:
  * Изолированная среда выполнения команд (`BashHarness`)
  * Защита от prompt-injection (`InjectionGuard`)
  * Фильтрация опасных bash-команд (`YOLOClassifier`)

## 2. Структура проекта и импорты

### 2.1. Важная особенность импортов (`core`)
В проекте исторически используется путаница с импортами. Модули обращаются к ядру через `core`, например:
```python
from core.logger import logger
from core.event_bus import EventBus
```
Но физически все исходные файлы лежат в директории `ml_workers`.
* В корне проекта **обязательно должна существовать символическая ссылка** `core -> ml_workers` (`ln -s ml_workers core`).
* При написании новых файлов импортируйте модули через `core` (например, `from core.db import ...`) или используйте относительные импорты внутри папки `ml_workers` (например, `from .db import ...`).
* Конфигурация `pytest.ini` настроена с `pythonpath = . core`, что позволяет pytest корректно разрешать импорты.

### 2.2. Архитектура папок
* `ml_workers/` — корень исходного кода Python.
  * `ml_workers/core/` — гексагональная бизнес-логика (Domain & Application).
    * `ml_workers/core/domain/` — доменные модели (Pydantic-схемы, контракты данных).
    * `ml_workers/core/application/` — прикладные сервисы, оркестраторы задач.
  * `ml_workers/adapters/` — адаптеры для внешних интеграций.
  * `ml_workers/infrastructure/` — драйверы баз данных (SQLite, Kùzu, LanceDB), настройки Redis и модели MLX.
  * `ml_workers/tests/` — тестовое покрытие (каждый файл теста соответствует модулю с префиксом `test_`).
  * `ml_workers/rules/` — правила валидации и подсказки (Prompts).
  * `ml_workers/tools/` — системные инструменты и интеграции.
* `wiki/` — центральная база знаний проекта (все *.md файлы пишутся на русском языке).
* `proto/` — gRPC протоколы и сгенерированные файлы (`morphs.proto`).

## 3. Соглашения об именовании (Naming Conventions)

Соблюдайте стандарты PEP 8 с некоторыми уточнениями:
1. **Имена файлов и модулей**:
   * Всегда `snake_case` (например, `event_bus.py`, `plan_tracker.py`).
   * Специализированные агенты (Morphs) должны оканчиваться на `_morph.py` (например, `security_morph.py`, `reactor_morph.py`).
2. **Классы**:
   * Всегда `CamelCase` (например, `YOLOClassifier`, `BashHarness`, `EventBus`).
   * Исключения для аббревиатур допускаются (`AST`, `RL`), но предпочтительнее делать их частью CamelCase (`KuzuDashboard`, `AtroposRL`).
3. **Функции, методы и переменные**:
   * Всегда `snake_case` (например, `execute_command()`, `task_id`).
4. **Тесты**:
   * Имена тестовых файлов: `test_*.py` (например, `test_yolo_classifier.py`).
   * Тестовые классы (если используются): `Test*`.
   * Тестовые функции: `test_*` (например, `test_yolo_classifier_blocks_rm_rf`).

## 4. Языковые стандарты и комментарии

* **Язык общения и документации**: Все обсуждения, ответы пользователю, отчеты и файлы в директории `wiki/` должны быть строго на **русском языке**.
* **Комментарии в коде**: Допускается писать docstrings и комментарии как на английском, так и на русском языке, но предпочтительно поддерживать единообразие с окружающим кодом. Если вы меняете существующий файл — пишите комментарии в стиле автора файла.
* **Логирование**: Логи должны быть информативными. Сообщения логов обычно пишутся на английском языке для системной консистентности.

## 5. Правила работы с кодом и тестами

1. **Запрещены плейсхолдеры**:
   * Никогда не оставляйте `TODO`, `FIXME` или `pass` в местах, где должна быть логика. Пишите рабочий, законченный код.
2. **Безопасность выполнения**:
   * Любые системные вызовы через `subprocess` или выполнение bash-команд должны проходить через `BashHarness`.
   * Избегайте прямого использования небезопасных команд на хосте. Помните о песочнице и ограничениях безопасности (`YOLOClassifier`).
3. **Тестирование перед коммитом**:
   * Все новые функции должны покрываться тестами в `ml_workers/tests/`.
   * При изменении существующего функционала обязательно запустите тесты для проверки на регрессии.
4. **Линтинг и форматирование**:
   * Перед завершением работы обязательно отформатируйте и проверьте код с помощью Ruff.

## 6. Полезные команды

Запуск команд производится из корня проекта:

* **Запуск тестов**:
  ```bash
  pytest
  ```
  Или для запуска конкретного файла тестов:
  ```bash
  pytest ml_workers/tests/test_event_bus.py
  ```

* **Проверка качества кода (Ruff)**:
  ```bash
  ruff check ml_workers
  ```

* **Автоматическое форматирование кода**:
  ```bash
  ruff format ml_workers
  ```

* **Запуск Core Mind FastAPI сервера**:
  ```bash
  python ml_workers/main.py
  ```

## 7. Соглашения по коммитам (Commit Conventions)

Используйте формат Conventional Commits на русском или английском языке:
* `feat: ...` — добавление нового функционала.
* `fix: ...` — исправление багов.
* `docs: ...` — обновление документации.
* `refactor: ...` — рефакторинг кода без изменения логики.
* `test: ...` — добавление или изменение тестов.

*Пример*: `feat: добавлено автоматическое восстановление соединения в Redis EventBus` или `fix: исправлена ошибка импорта core.db в test_db.py`.
